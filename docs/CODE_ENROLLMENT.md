# One-use code enrollment

The new independent Authority supports first installation followed by pairing, and
additional Mac pairings after installation. It keeps its existing Windows identity,
service accounts and protected stores. An RDP session is not required.

The Windows setup's connection-code screen accepts the single `jts-pair://enroll`
URI generated by the Mac. The code contains a random 256-bit secret; it is not a
six-digit password. The existing per-device AI-control setting is the owner's
pairing delegation. There is no second trust-confirmation dialog. Windows elevation
for installation and machine-level local management remains an OS boundary.

For automation, `--enroll-code` reads one bounded code line from standard input,
never argv or a request file. `--status` returns public status JSON, and `--manage`
opens the same management screen. A new machine can install and submit the code in
one flow; an installation already running this version sends the code to its live
Authority. An older Authority without the management endpoint needs an explicit
upgrade path; the first-install transaction must never overwrite its state.

## Trust and encryption

Both endpoints derive independent offer, response and relay-claim keys with
HKDF-SHA256. AES-256-GCM encrypts the exact delegated request and public Windows
response. The relay receives only the derived claim token and encrypted envelopes.
The Windows device signs the exact claim transcript with its existing P-256 key.
Outer HTTPS retains the owner-selected certificate-validation default; this does
not change the pinned inner mutual-TLS requirements. Windows 10/Server 2019 TLS
1.2 compatibility remains an explicit request field, never a network fallback.

The authority validates the invitation, canonical origin, peer SPKI hash, distinct
grant IDs, exact request bytes/hash and expiry. A code cannot replace an existing
current pairing or reuse a revoked pairing epoch. New controller identities can
be added without changing the local Windows identity.

## Durable lifecycle

1. The accepted attempt is encrypted with the Authority account's CurrentUser DPAPI.
2. The fetched encrypted offer and the exact generated response/signature are saved
   before claim submission. Retries after lost responses reuse those same bytes.
3. `claimed` means the Mac still needs to verify and confirm the response. Windows
   has not activated any grants or lanes.
4. A `bound` receipt must carry the Mac's P-256 signed v2 confirmation, binding
   the exact relay origin, invitation, both device identities, claim hash and
   original import window. The Authority verifies this signature independently;
   a relay-supplied state string cannot authorize a commit. The signed confirmation
   is saved in the durable local commit journal and checked again on recovery. Control
   grants are persisted first and the pairing last; this prevents partial grants
   from authorizing business channels. A crash at either boundary resumes the
   same idempotent commit, even after the original code's import window expires.
   The exact new pairing epoch is activated in the live runtime before `bound` is
   reported; superseded sessions are drained and revoked grants/jobs remain denied.
5. Established trust remains until explicit revocation. RDP credentials, listener
   availability and login failures do not consume or revoke a pairing.

Unbound attempts still expire at the invitation's deadline. Receipt lookup occurs
before local expiry handling so a successfully bound claim whose response was lost
remains recoverable. Network loss retains the pending attempt and resumes after
reconnect/reboot. Each HTTPS exchange has a deadline covering headers and body.
There is one pending attempt at a time and bounded retained
history. State is under the existing protected authority directory as
`enrollment-attempts.sealed`; plaintext codes and private identity material are
never exported. Corrupt authenticated state is not silently reset.

Remote revocation uses an authenticated signed mailbox, independently of RDP or
an active control stream. The Mac signs the exact relay origin, both identities,
pairing epoch and all three capability IDs. Windows checks the controller key
against its saved identity, seals the request before applying it, tombstones the
pairing and control grant, cancels detached and queued tasks, then waits for
sessions and the active executor to drain. Only then does it persist and send a
Windows-signed completion receipt. Lost replies retry the same saved receipt;
offline requests remain pending. Reboot does not restore a revoked epoch. A
late old-epoch request cannot stop a newer pairing. The Mac may report confirmed
revocation only after verifying the matching Windows receipt.

All signed relay HTTP operations use authentication v2 with the canonical relay
origin in the signature transcript. There is no v1 fallback. Upgrading endpoints
and a node therefore requires a coordinated v2 rollout; a v1 node is not accepted
as a security-compatible carrier.

## Local management boundary

The runtime owns the databases and handles management over a bounded named pipe,
`JTSCompanionEnrollment25`. No second process opens the live DPAPI/SQLite stores.
The pipe has a protected DACL, rejects remote clients, keeps its first-instance
handle open, and exposes only status, enroll and revoke. The server checks the
actual client token's SID, administrator membership, elevation and nonzero session
against the pipe client's process session; message fields cannot assert identity.
SYSTEM, service-session clients and non-elevated users are rejected. The client
uses identification-only SQOS, validates the server PID against the running SCM
Authority service, and verifies its protected manifest-pinned executable before
sending a code. Responses use a bounded read acknowledgement before disconnecting,
so buffered replies cannot be silently discarded. The management plane carries no
arbitrary command operation.

Current-user DVC and machine-level Relay Authority keep separate identities and
permissions. An already authorized remote command path may invoke the management
CLI within its normal Windows elevation boundary. This protocol does not promote
an ordinary DVC user or allow the script Worker to edit Authority trust.

## Verification boundary

The portable tests cover an independent Python cryptographic vector, substitution,
strict parsing, interrupted claims, restart at each local commit boundary, expiry,
revocation and independence from RDP. Windows-only tests exercise actual pipe token
inspection and rejection of an impostor server before any secret is sent. These
checks do not replace installation, live SCM/account/profile behavior and a full
Mac → relay → Windows acceptance run on the intended target OS.

## Upgrading an existing code journal

Before creating an executing control host, Authority replays durable revocation
intents into pairing/grant tombstones. An older code journal marked `bound` or
`committing` without a signed v2 Mac confirmation is retired with
`ENROLLMENT_LEGACY_CONFIRMATION_REQUIRED`; generate a fresh code to pair again.
The Windows identity and unrelated devices remain intact. This does not reinterpret
an explicit local JSON installation with no code journal as relay confirmation.
No upgrade or recovery path generates a revocation completion before the live
runtime has confirmed that the old executor and sessions stopped.
