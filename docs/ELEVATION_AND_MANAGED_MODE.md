# Elevation and Managed Mode

This document defines the Windows privilege boundary for JTS Terminal 2.0. Both modes use local named pipes only. They do not listen on TCP or UDP, do not expose an administrator password API, and do not give the AI a way to approve Windows secure-desktop UAC.

The 2026-09-05 owner decision removes mandatory Authenticode but retains
administrator/UAC capability. Runtime release identity now uses a project-owned
P-256 manifest with a compiled public-key trust anchor. It does not remove
Windows consent or OS security policy. See [Distribution policy](DISTRIBUTION_POLICY.md).

## Standard interactive UAC broker

The current-user Companion remains unelevated. A request is accepted only when all of these fields are present and within policy:

- Full PowerShell script, limited to 64 KiB.
- Configured root ID and a relative working directory that resolves without traversal, symlinks, or reparse points.
- One to sixteen explicit read or read/write data scopes. Every scope is a configured root or an existing directory below one.
- Runtime from 100 ms through 15 minutes and output from 1 KiB through 128 KiB, leaving worst-case JSON escaping overhead below the 1 MiB DVC control-frame limit.
- Lease duration from 1 ms through 15 minutes.
- A scrubbed environment whose names cannot look like password, secret, token, private-key, access-key, or credential fields.

The Agent canonicalizes the script, resolved working directory, limits, sorted environment, and sorted data scopes into JSON and hashes the bytes with SHA-256. It then shows the complete script, directory, duration, and every data scope to the interactive Windows user. Declining returns `ELEVATION_DECLINED`.

After that explicit pre-consent, the Agent starts the installed broker with `runas`. Windows owns the UAC secure desktop and credential UI. The Companion sends no keystrokes to it, cannot read a password, and has no protocol method for approving it. Cancellation returns `UAC_CANCELLED`; timeout returns `UAC_TIMEOUT`.

RDP itself can carry input to a Windows secure desktop. Therefore the macOS controller has a mandatory interlock: from immediately before sending `elevation.request` until approval, cancellation, timeout, or failure returns, every AI-originated `desktop_action` must fail closed while locally generated human input remains available. The Windows broker cannot distinguish RDP packets generated by an AI from packets generated by the person at the Mac. The .NET source in this directory does not claim that this macOS-side interlock is already Windows-validated.

The Agent creates a random one-client `PipeOptions.CurrentUserOnly` pipe and launches one broker for one lease. The OS-reported peer PID must match the process returned by `runas`. Agent authenticates its adjacent release manifest using Core's compiled public key and checks its own bytes before configuring elevation. Before consent/launch, it opens the exact Broker role from that same immutable inventory and holds a read-only, no-write/no-delete-share file lock. The elevated Broker independently validates itself, discovers the actual pipe-server PID, and checks the exact `JTS.WindowsCompanion.Agent.exe` bytes against its own authenticated inventory, keeping the peer image locked for the session. A peer cannot substitute its own different manifest or an editable checksum. The 256-bit random nonce is checked on every length-prefixed message.

The Broker issues a maximum-15-minute lease containing one `ApprovedPowerShell` action ID and the canonical payload digest. The Agent also creates a random per-broker cancellation event. Companion control requests are dispatched concurrently with serialized outbound DVC framing, so `elevation.release` is not queued behind a running script. Release, Agent shutdown, or DVC failure signals the event; the Broker cancels and kills the PowerShell process tree before exiting.

Lease deadlines are active rather than query-driven. `ElevationLeaseManager` uses a `TimeProvider` timer for every issued lease and cancels the lease execution token at the exact deadline; explicit revoke uses the same token. The Broker links that token to every phase of execution: process launch, standard-input delivery, bounded standard-output/error reads, and process wait. Cancellation at any phase enters one non-cancelable cleanup path.

Elevated execution requires:

- `requiresElevation: true`
- the exact `elevationLeaseId`
- the exact `elevationActionId`
- every approved script, path, limit, environment, and scope field unchanged

Any mismatch returns `NOT_AUTHORIZED`; the script is not launched. The elevated Broker passes the script through standard input to `powershell.exe -NoLogo -NoProfile -NonInteractive -Command -`, uses the approved working directory, a restricted environment, bounded output, and the approved deadline. Closing the DVC/Agent disposes the private pipe, signals cancellation, and terminates the broker session. `elevation.release` immediately signals the same cancellation path. There is no reusable administrator shell. Concurrent requests with the same idempotency key are coalesced before handler execution, so enabling urgent release does not duplicate an exact elevated action.

On Windows, PowerShell is assigned immediately after launch to a private Job Object configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Normal completion closes the job after the process exits. Cancellation, timeout, launch/pipe/read/write failure, or broker shutdown closes the job first, waits for process exit, and then uses `Process.Kill(entireProcessTree: true)` as a bounded fallback. Failure to create or assign the Job Object fails closed and kills the launched process. The production process factory is unavailable off Windows; platform-neutral tests use the same lifecycle interface with controlled fake processes instead of weakening containment.

Cancelling the pre-UAC consent token posts `WM_CLOSE` to the consent window and surfaces `OperationCanceledException`; the dialog is not left behind. Once a broker has started, cancellation always sets the private event and closes the pipe, waits up to five seconds for graceful broker exit, then terminates the broker process tree and waits another five seconds. Lease release deliberately completes this safety cleanup even when the requesting cancellation token is already cancelled.

Protocol order:

1. `elevation.request` with `{ execution, durationMilliseconds, dataScopes }`.
2. Windows full-script approval and UAC.
3. Response `ElevationLease`; read `leaseId` and the single returned `actionId`.
4. `shell.exec` with the unchanged execution plus `requiresElevation`, `elevationLeaseId`, and `elevationActionId`.
5. `elevation.status` or `elevation.release` with `{ leaseId }`.

## Release identity and optional Authenticode

`ReleaseManifestTrust` authenticates `JTS.WindowsCompanion.release.json` with an
ECDSA P-256 public key embedded in Core through `CompanionReleasePublicKeyPath`.
The release private key stays outside the source tree and package. The signed
payload binds `schemaVersion`, `releaseId`, and exact `fileName`/`sha256` entries;
its envelope carries the base64 payload and P1363 ECDSA/SHA-256 signature.
Malformed or oversized manifests, unknown/duplicate fields, wrong keys, unsafe
names, reparse points, unlisted roles, and modified files fail closed. Production
entrypoints do not accept a runtime replacement key or unsigned fallback.

Setup validates its bounded embedded manifest before extracting executable
payloads, installs that manifest with Agent/Broker in one directory transaction,
and revalidates the activated inventory before committing and launching Agent.
Its own final hash cannot be inside the embedded manifest without a circular
dependency. Initial Setup provenance is the exact installer hash carried inside
the Apple-signed Mac app or another independently trusted release channel.
`LockedExecutableCopy` compares staged/detached copies against the locked running
source; it proves copy continuity, not an independent publisher identity.

The publisher requires an external `ReleasePrivateKeyPath` (or
`JTS_RELEASE_PRIVATE_KEY_PATH`). The independent release tool provides explicit
`keygen`, `public-key`, and `sign` operations; no production key was generated by
this change. `-AllowUnsignedDevelopmentBuild` is diagnostic-key packaging only,
not a release shortcut. Optional Authenticode requires both certificate
thumbprint and timestamp URL; any requested signing failure remains fatal.

`WindowsAuthenticodeTrustVerifier` remains strict and available as an additional
policy: it delegates Windows chain/revocation/timestamp validity to
`WinVerifyTrust`, rejects reparse-point binaries, requires the expected file
name, and requires an exact signer subject and SHA-256 certificate fingerprint.
The new release-identity path does not weaken or turn that verifier into a
successful no-op. DVC pairing and message signatures are separate security
mechanisms and are unchanged.

## Optional managed service

`JTS.WindowsCompanion.ManagedService.exe` is a conventional Windows service hosted through the Service Control Manager. It runs in non-interactive Session 0 and never exposes UIA, mouse, keyboard, or desktop methods.

Managed mode is still an optional, unshipped source path. The normal current-user
Setup does not install a service. A separately approved administrator installer
must write `managed-service.json` next to the service executable in its protected
installation directory:

```json
{
  "pipeName": "JTS.Terminal.Managed.v1",
  "allowedClientSid": "S-1-5-21-...",
  "manifestDirectory": "Manifests",
  "handlerDirectory": "Providers"
}
```

The service creates the pipe with a protected DACL containing only LocalSystem full access and the configured interactive-user SID read/write access. It also impersonates each connected pipe client and compares the effective SID before reading a request. `PIPE_REJECT_REMOTE_CLIENTS` rejects remote named-pipe access. Before transmitting a request, Agent verifies the OS-reported server PID against SCM, the registered/running path, LocalSystem SID, Session 0, and service-token state, then verifies the service's exact release-pinned bytes. The service independently attests its own SCM startup identity and authenticated release.

Each provider is an installer-written JSON file in `Manifests`:

```json
{
  "providerId": "vrc-factory",
  "version": "1.0.0",
  "handlerExecutable": "vrc-factory-managed-provider.exe",
  "handlerSha256": "<64 hex characters>",
  "operations": [
    {
      "operationId": "clean-install-auto",
      "acceptedArguments": ["jobId", "packagePath"],
      "allowedRootIds": ["factory"],
      "maximumDurationMilliseconds": 1800000
    }
  ]
}
```

Startup rejects manifest/handler traversal, links, reparse points, duplicate providers/operations, invalid hashes, and operation or argument names containing `script`, `shell`, `powershell`, `command`, `executable`, or `arguments`. Before every launch, the service holds the handler image locked and rechecks both the fixed-operation handler SHA-256 and its entry in the service's authenticated release inventory. It starts the fixed handler directly with `UseShellExecute=false`, passes only `--managed-operation <installed operationId>`, and sends validated structured arguments over standard input. It never starts `cmd.exe`, `powershell.exe`, or an executable supplied by a task.

The interactive Companion exposes `managed.execute` only when `--managed-service-pipe` is configured. The service independently enforces the installed provider, operation, accepted argument names, allowed root IDs, and maximum deadline; Companion configuration cannot broaden them.

The installer must:

1. Install service and provider binaries under the expected administrator-protected directory; this does not change normal current-user Setup into a machine installer.
2. Publish service and participating apphosts with the designated compiled release public key, include every expected service/handler role in the authenticated release inventory, and install matching manifests alongside the participating executables. Authenticode may be an additional policy, not a prerequisite.
3. Set the service configuration, manifests, and handler directories to LocalSystem/Administrators write access only.
4. Write the intended interactive user SID into `managed-service.json`.
5. Register `JTSWindowsCompanionManaged` with the Service Control Manager under LocalSystem and configure normal recovery policy.

## Verification status

Local macOS build and tests cover platform-neutral payload, digest, lease, IPC
framing, authenticated manifest, same-release image, locked-copy continuity,
and rejection policies. The [release test inventory](../tests/JTS.WindowsCompanion.Tests/release-test-inventory.json)
records current cases and named skip policies; Windows-only skips remain
explicit. This does **not** prove Windows UAC, SCM, SID ACL, DPAPI, WTS DVC,
Windows file-lock semantics, or Windows 10/11 behavior.

The platform-neutral suite also advances a manual `TimeProvider` to prove that expiry cancels a running execution without a status query, proves explicit revoke uses the same path, cancels the executor independently at launch/input/read/wait stages, and verifies graceful-versus-forced broker shutdown. These tests validate orchestration and fail-closed behavior; Windows Job Object and consent-window behavior still require the real Windows runner below.

The Windows release runner must still perform:

- Windows 10 x64 and Windows 11 x64 build/test/publish.
- Authenticode-free positive release execution plus altered/unknown-key manifests, unlisted or modified executables, different-release peers, reparse paths, and replacement-while-locked rejection. If optional Authenticode is selected, retain its valid-signer positive and unsigned/wrong-publisher/expired/revoked negative checks separately.
- Full-script consent followed by accept, decline, UAC cancel, UAC timeout, secure-desktop password entry, and proof that the macOS elevation-pending interlock rejects AI RDP input while human input remains available.
- Exact-payload success plus changed-script/path/scope/timeout rejection and 15-minute expiry.
- Pipe ACL checks for intended user, second local user, Administrator, remote client, wrong process, and pipe squatting.
- For separately shipping managed mode: service install/start/stop/recovery, protected installation ACLs, fixed provider success, uninstalled operation rejection, handler hash/release-entry change rejection, and proof that no UIA/desktop interaction occurs in Session 0.

The QA executable now emits schema-3 project-manifest diagnostics and requires
a `qa-elevation-` release ID. Its migrated PowerShell harness and the separate
diagnostic Setup builder use temporary project keys without importing trusted
certificates; both still require real Windows runs. Earlier signed-UAC results are historical
evidence, not acceptance of this new path. No production release private key or
complete Windows 10/11 release-matrix evidence set has been provisioned by this
change. Lack of a commercial Authenticode certificate is not a release blocker;
the remaining real-machine and artifact-provenance gates are.
